Question: does the frozen static scene keep valid camera output across complete RDT/T5/SigLIP loading and one synthetic B1 prediction when model computation and EGL rendering have separate process state on the same physical GPU3? The latter failed at its first post-load frame with owned Xid31 despite successful environment/context release on the render thread. These observations motivate process isolation without establishing the root cause. No unsuccessful intervention has been applied as a production repair.

One fixed intervention relative to original82981d: one model parent and one fresh multiprocessing spawn renderer, sharing only a synchronous command/evidence pipe. Do not fork an initialized CUDA/EGL process. The renderer alone constructs, initializes, renders, closes and releases the environment/context. The parent executes the original load_policy and predict_once operations unchanged, exactly one B1, on its main thread. No concurrent scene/model operations: the parent waits for each render boundary, and the renderer waits while model loading/inference occurs. No native handles or exception tracebacks cross processes; transmit only commands and ordinary CPU scalar metadata/hashes/counters. This is one GPU reservation and one logical engineering worker with two owned processes, both exclusively physical GPU3, never GPU3 plus another card.

Before any renderer GPU operation, its startup handshake returns PID, PPID, PGID, session ID, start ticks and boot ID. The model parent verifies direct-child identity, shared owned process group/session and immutable process identity, writes renderer-process.json durably with the resource/contract identity, then acknowledges startup. The supervisor incorporates that validated child into ownership monitoring before accepting GPU activity from it. Watch exact GPU3 Xid31/109 for both model and renderer, retaining identities after exit for delayed kernel records.

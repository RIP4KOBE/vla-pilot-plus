### Existing recorder is not a deployed feedback mechanism

`DecisionEvidence` is write-only for policy (`core/decision_evidence.py:1`, `:71`). The following events retain existing values without another environment/provider call:

- `decision_context`: stage, keypoints, provider identity, and `target_observation="existing_chunk_keypoint_read"` (`:174`). Provider identity includes wrapper/original code hashes and existing loader text/path metadata (`:47`).
- `action_dispatch`: current decision ID, global step and one-based execution index (`:238`); `executed_action`: final `action_numpy` (`libero_adapter.py:1712`).
- `pre_reset_outcome`: native `robot0_eef_pos`, `robot0_eef_quat`, gripper qpos/qvel, original reward, terminated/success; **`contemporaneous_target_pose=None`** (`decision_evidence.py:247`).
- `automatic_reset_boundary`: `reset_will_follow=True`, `reset_completed=None`, flushed before reset (`:255`). `step_returned` subsequently records termination/truncation/success and flushes (`:261`).

Events carry `episode`, `decision_id`, `global_step`, and `reset_sequence` (`:142`). The terminal outcome/reset-boundary events use the old reset sequence; the subsequent `step_returned` uses the incremented sequence. A future reader must preserve this explicit transition rather than requiring identical reset-sequence values across the terminal pair. No event claims that reset completed before it actually returned. The current selector does not read these files or collector outcome buffers.

Snapshots retain source tensor/array dtype (`decision_evidence.py:25`). The source raw EEF dtype must be read from evidence, not assumed here. A BF16 projection promoted for analysis remains a BF16-origin quantity; it does not gain physical precision. The projector's controller source and dtype-cast start are separately recorded (`libero_adapter.py:1677`).

## Conditional interface proposal — not implemented or selected

If completed evidence later supports investigating Hypothesis B, the smallest causal plumbing would be an explicit policy-owned history receiver and a read view at fresh selection. No estimator, selection rule, parameter, retention length, or target-specific mechanism is chosen by this report.

An adequate transition contract would distinguish: episode/reset generation; originating decision and action-step/index; stage/guidance/provider identity; **the command actually sent**; old-episode raw EEF/gripper fields and native dtype/source; completed-return vs missing outcome; terminal/truncation flags. Target data could refer to the already available chunk keypoint observation and its observation time, with per-action target pose remaining Unknown. Existing controller projection anchors would retain separate provenance; they must not silently replace sensor outcomes. Original environment reward remains a distinct field from guidance-provider quality. Success/terminal metadata can define lifecycle boundaries without becoming a ranking oracle.

The narrow attachment points would reuse outer adapter `action_numpy`, inner `raw_obs` **before** automatic reset, and the outer returned truncation flag. Only completed transitions preceding a selection can be visible to it. The history receiver should not read diagnostic logs, query `_get_raw_obs`, re-run providers/projectors, or access task/evaluator hidden state. **`LiberoAdapter._get_raw_obs()` actually calls `robosuite_env.step(np.zeros(7))` (`libero_adapter.py:1137`) and is not a permissible read-only feedback getter.** This review proposes no changes to that function.

An explicit physical-reset notification plus explicit stage/guidance/provider/target-generation metadata is missing from the selector API. A future implementation would have to define those boundaries, unavailable-data behavior, source-frame/dtype rules, and the exact pre-selection cutoff prospectively. Task ID or future endpoint/success must not be introduced as a selection feature. A terminal or failed/pending transition cannot be silently substituted with the reset state or zero feedback. Initial EEF can use already existing observation/projection locals; it does not justify an additional native read or projection call.

Meaningful CPU gates for such a future interface would be: (1) an actual stubbed Main/policy/adapter prefix exposes only earlier completed steps and gives the first decision no history; (2) terminal reset mutating observation arrays cannot overwrite the old EEF, and truncation/pending failure preserve prefix length; (3) episode reset and stage/guidance boundaries behave exactly as the prospective contract states; (4) instrumentation leaves the original command, RNG and model/provider/projector/step/reset/render call sequence unchanged. These tests were **not run** because this task makes no implementation. They would not establish GPU equivalence, tracking causality, benefit, or that Hypothesis B is true.

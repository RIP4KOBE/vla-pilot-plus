# Phase 2 Hypothesis Discrimination

**Date:** 2026-04-30
**Evidence round:** 1
**Generated by:** loop_comparison.py + image_check.py

H2 (lang embedding zero):        REJECTED                           — evidence: norm=16.98, two tasks produce distinct embeddings (first-token diff=7.45)
H3 (image flip):                 CONFIRMED                          — evidence: torch.flip(dims=[2,3]) in LiberoProcessorStep source confirmed

## H1 — Denoising Loop Bias (Revised Understanding)

**Original hypothesis:** zero-padding causes random noise output.

**Actual finding (from loop_comparison_output.txt):**

- Both official `step()` and custom `_predict_unguided()` produce **temporally smooth, highly autocorrelated** trajectories (autocorr official = 0.9472, custom = 0.9810).
- However, they converge to **different joint configurations** — mean abs difference in normalized joint space = 0.608 (on a scale where ±1 spans the full joint range).
- Specifically, official per-dim normalized step-0: [-0.500, -0.660, -0.164, -0.723, 0.102, -0.063, -0.574]
  Custom per-dim normalized step-0:              [-0.734,  0.523,  0.104,  0.590, -0.008, -0.871, -0.961]
- Several joints have opposite signs — e.g., joint 1: official = -0.660 (near home), custom = +0.523 (away from home, close to limit).

**Why this causes failure:**

1. The custom loop converges to a wrong joint configuration far from the LIBERO task-relevant workspace.
2. The action converter computes FK deltas between the LIBERO start config and the predicted (wrong) config. The delta is huge → step-0 action is saturated at ±1 (seen in evidence: 2/24 position dims hit ±1.0 on step 0).
3. Steps 1-7 have near-zero deltas (trajectory barely moves after step 0) → robot stalls after the first move.
4. If `generate_new_chunk=True` every step: robot repeatedly tries to reach the same wrong config → oscillates.

**Root mechanism:**

The zero-padded inactive 120 dimensions in `x_unified` during denoising push the posterior toward a different attractor than full-128D noise. The model's self-attention across the 256D `[action | mask]` token is sensitive to these zeros. The result is a biased but smooth trajectory targeting a wrong joint configuration.

**Confirmation status:** CONFIRMED — the custom loop produces substantially wrong joint targets compared to the official inference path.

## H2 — Language Embedding Zero Fallback

**Finding:** REJECTED.

- `encode_instruction` returns norm = 16.98 for LIBERO task "open the top drawer of the cabinet".
- Two different tasks produce measurably different embeddings (first-token diff = 7.45).
- 9 md5-named `.pt` files in `data/rdt_lang_embeds/` and checkpoint `lang_embeds/` confirm T5 was successfully computing embeddings during prior runs.
- The cache key mismatch (file stem vs md5 hash) is a non-issue because the code saves new embeddings with the md5 filename, so subsequent loads work correctly.

**This bug does not exist in practice for runs after the first call per task.**

---

## H3 — Image Orientation Flip

**Finding:** CONFIRMED.

- `LiberoProcessorStep._process_observation` applies `torch.flip(img, dims=[2, 3])` to all images.
- This flips both spatial dimensions → 180° rotation.
- All images entering `RDTSteer` are upside-down relative to ManiSkill training distribution.
- The SigLIP image encoder was trained on upright SAPIEN images; flipped inputs produce wrong spatial features.

**Impact assessment:**

- This bug **degrades** visual conditioning quality but does NOT cause random motion by itself.
- The model still receives coherent (but inverted) spatial information — it encodes object positions as if the scene is upside-down.
- Combined with H1 (wrong joint configuration target), this removes any chance of task-relevant behavior.

---

## H4 — FK OSC Scale Wrong

**Finding:** MINOR — not the primary cause.

- `pos_max = 1.0` for 2/24 position dimensions (step 0 only).
- Mean position action = 0.120 across all 8 steps — within expected range for a non-trivial motion.
- Steps 1-7 show tiny deltas (e.g., pos=[0.002, 0.015, 0.020]) — near-zero motion.

**Root cause of saturation:** The saturation at step 0 is not primarily due to wrong `_POS_SCALE`. It is caused by the large joint-space gap between the LIBERO start configuration and the RDT model's predicted (wrong) target configuration. Adjusting `_POS_SCALE` alone would not fix this if H1 remains unfixed.

**After H1 is fixed** (correct joint targets), the FK deltas should be smaller and saturation may disappear naturally. The scaling should be re-evaluated with H1-corrected output.

---

## Primary Cause Assessment

Both H1 and H3 are independently confirmed and likely compounding:

| Bug | Mechanism | Impact |
|---|---|---|
| H1 (denoising bias) | Custom loop converges to wrong joint config (0.61 normalized diff from official) | Robot moves to wrong region of workspace, then stalls |
| H3 (image flip) | 180° rotated images → wrong visual conditioning | Model cannot use spatial features for task understanding |

**The combination produces behavior that looks like "random, task-unrelated motion":**
- Robot makes a large move toward the wrong config (step-0 saturation)
- Barely moves for subsequent steps (near-zero FK deltas)
- With fresh chunk every step: oscillates near the wrong config
- Visual conditioning is corrupted → no correction signal

## Repair Readiness

**YES — repair readiness criteria are met:**

- [x] H1 status: CONFIRMED with exact mechanism (8D noise vs 128D noise → biased denoising posterior)
- [x] H2 status: REJECTED
- [x] H3 status: CONFIRMED with exact code location (`LiberoProcessorStep._process_observation`)
- [x] H4 status: MINOR, secondary to H1

**Fix order (do not bundle):**

1. **Fix H1 first:** In `_predict_unguided` and `_guided_denoise_loop`, initialize `x_t` in the full 128D unified action space (same as `conditional_sample`), not the 8D subspace. This is a single-line change.
2. **Validate H1 fix:** Run 1 episode and confirm action distributions match the official path more closely.
3. **Fix H3 second:** In `RDTObsProcessor._tensor_to_pil`, flip images back before passing to the model. Alternatively, bypass `LiberoProcessorStep`'s flip for the RDT policy path.
4. **Validate H3 fix:** Save one input image and confirm correct orientation.
5. **Re-evaluate H4:** With H1 fixed, check if step-0 saturation disappears. If not, investigate `_POS_SCALE` adjustment.

**Do NOT fix H3 simultaneously with H1** — fixes must be validated independently.

## 2. 保留与改变的条件

保留当前源码 C0 的权重、策略和环境配置：RDT-1B-LIBERO-Object EMA；LIBERO object-swap task 0–9；种子 `[44,235,43,546,6,621,197,87,151,548]`；主 seed 0；每任务 720 步；历史连续策略随机流；ED population 16、10 轮、非 CEM、temperature 0.1、renoise 3→1、absolute EEF RBF；QD archive 关闭；grounding 关闭。原 Stage 模板、触发、解析器、夹爪时序及关闭后的处理均保持原样。

本轮指定变化是 `main.cached_functions_dir=null`，每个任务根据自身初始观测重新生成函数及阶段描述。生成客户端与 Stage 客户端均明确配置 Poe `gemini-3-flash`。生成保留原配置 temperature=1.0、max_completion_tokens=2000、stream=true；Stage 保持 temperature=0、max_tokens=256。

reward 的“在线生成”指每任务开始时新生成函数；后续数值由函数在本地对当前候选计算，不是每步向 API 请求 reward 分数。生成内容保存供审计，不等于从历史缓存加载。

遇到连接故障后，正式完整批次增加了下节明确记录的传输设置变化。未改原模型请求载荷、prompt、解析或 C0 控制算法。新模型、新生成程序和连续随机流下的结果不能称为严格复现历史 Gemini-2.5，也不能视为每个后续任务都拥有相同策略随机状态的纯单变量因果对照。

## 3. 中断与恢复经过

第一批 `attempt1` 完成 task 0–2（均失败），在 task 3、第 24 步的 Stage 请求中，经 3 次 HTTP 尝试后仍无完整回复，返回 APITimeoutError。监督程序停止该批，保存 4 个已启动回合及全部前缀证据；本批不计作十任务结果。

本机 SDK 默认连接超时为 5 秒；失败请求共耗时 16.34 秒，与连接阶段超时相符。但原异常因果链没有落盘，无法进一步证明具体超时节点。恢复时使用独立启动器将两个客户端设置为 connect 30 秒、read 180 秒、write/pool 60 秒、SDK 最多 5 次重试。只重试网络/API 临时故障，不因回复语义或格式不理想而重抽。

相同失败输入的连接探测在 8.74 秒取得完整回复，未用于任何正式动作。CPU 检查验证重试前后模型请求载荷一致、完整但不可解析的回复不会被重抽。随后从 task 0 重新生成并运行完整十任务，保留连续随机流，不使用第一批函数或回复，不拼接两批结果。

第一批占用上界 0.308651266 GPU 小时，完整批次 0.983442464 GPU 小时，总计 **1.292093730 GPU 小时**；包含中断批共 14 个启动回合。研究累计 204 个启动回合、18.795106731 GPU 小时上界。依用户此前预算不作为停止条件的指令，记账上限补齐到 304 以容纳已发生的 204 次及原 100 次保护额度；48 GPU 小时及验证/正式保护 24 小时不变。本记录不授权额外队列，其他研究未改动。

## 4. 取消缓存后，实际改变了什么

### 第一阶段函数确实重新生成且存在数学差异

新程序使用了当前物体名称与关键点，而非统一复用旧描述。CPU 探测将候选末端放在相同目标点及各轴偏移 0.1 米的位置，确认新函数存在不同的水平权重。完整批次 task 0 的水平偏移评分约为 -0.0225，历史函数约为 -0.01；task 3、9 约为 -0.04。task 2 还改用同一 salad dressing 物体的 keypoint 1 作为抓取点，不能将这种变化直接称为选错物体。

生成温度仍为 1.0，函数和描述随任务生成而变化；本批不是固定的一套新 reward 在十个随机重复上的统计验证。第一批 task 0 的函数与完整批次也不同，不能混用两批数值解释最终得分。

### 九个第二阶段函数仍显式返回零；一个例外也未带来成功

原 LIBERO 模板明确要求篮筐任务第二阶段返回 0。本批 task 0–6、8、9 共九个函数仍是显式常量零。task 7（milk）没有遵循这一模板要求，生成了候选末端到篮筐关键点中心的负平方距离 reward；该函数在 CPU 探测中能区分不同候选，但本任务只执行了 3 个第二阶段 ED 动作段，最终失败。

因此不能说所有新函数都一样，也不能说自动重新生成已经统一补齐了放置评分。milk 的一个失败案例也不足以否定一切非零放置 reward 的价值。

### ED 调用更多，但大量调用没有质量排序信号

| ED 动作段 | 106（11.8%） | 301（33.4%） |

| 第一阶段 ED 动作段 | 106 | 121 |

本轮 **58.8% 的 ED 动作段处于零 reward**，对应 task 0、1、4、6 的第二阶段。Stage 要求开启引导，但实际函数不能区分候选的放置质量；多样性搜索仍会执行，不能将它等同于有效的放置优化。301 次中的其余 124 次有非零评分，也不能仅据此认定评分对应真实任务完成质量。

新阶段描述中，有些任务明确写“不需要第二阶段 guidance”，另一些只写“放入篮筐”；这与实际 Stage 开关及零函数组合呈现不同表现。观察说明二者的一致性需要控制协议约束，不能从文字相关性直接量化其对成功率的因果贡献。

## 5. 错误完成判断仍然存在

最清晰的案例是历史成功过的 task 3。新生成条件下，第 16 步进入 stage 2/off，第 96 步返回：

> The gripper just opened and the bbq sauce is now inside the basket; the task is complete, so no further stages or guidance are required.

但[本次请求的真实当前图像](../../../artifacts/c0_poe_fresh_20260929/outputs/c0_poe_fresh_attempt2/captured_stage_inputs/request_0054/image_02.png)清楚显示：带 BBQ 标识的瓶子仍在篮筐左侧，篮筐为空。本任务只有 2 个第一阶段 ED 动作段，随后 88 段均无引导，最终失败。

task 0–8 都至少一次输出 stage 0，但十任务最终均失败。task 9 从未输出 stage 0，仍失败，说明错误完成判断不是所有失败的唯一原因。既有夹爪首尾命令错位本轮也出现了 8 次记录事件；其来源和关闭后复查缺口此前已由源码及 CPU 探测确认，本轮未修改。

视觉案例是对保存图像的离线检查，未将环境成功真值或额外标注注入在线算法。

## 6. 本轮可以支持的结论与下一步

1. **请求的完整在线测试已完成且有效。** 本轮不是 0/3 或半途结束；最终报告使用独立完整十任务，0/10。
2. **仅取消旧缓存、重新生成内容，没有恢复历史性能。** 新内容确实改变 reward、描述和 ED 开关，但本批没有成功率收益。不能进一步断言缓存永远无关或某个模型永远不可用。
3. **新 Poe 接口可完成整个流程。** 传输问题已经单独处理，完整批次没有缺失回复；当前主要研究问题转向 Stage 事实判断、状态切换与实际评分的一致性。
4. **优先修确定的输入时序和控制缺口。** 正确使用最近执行的夹爪信息，区分命令和抓取证据；关闭引导后仍能复查；篮外释放不能直接判完成；零评分阶段的 guidance 语义需要明确。要研究放置优化，再单独验证非零评分，而非把它与所有控制修改混为一个条件。
5. 为下一轮公平比较，应固定经过验证的每任务 reward/描述，并对参考与修复条件统一逐任务策略随机数协议；Stage 仍基于当前观测在线判断。该建议属于后续方案，本轮没有自动实施或启动新的 QD/ED 实验。

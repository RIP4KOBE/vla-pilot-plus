# C0 未严格复现的原因与历史 Stage 回放结果

> 后续更新：当前源码也已在同一固定历史 Stage 回复条件下完成十任务回放，得到 3/10，十个视频和 127 条 Stage 事件均与原实验一致。详见[当前源码最终报告](2026-09-28-current-source-report.md)。

> 结论：历史源码在 GPU2、当前软件环境下，回放原始 Poe/Gemini 的逐次原文回复后，**精确恢复 3/10（task 3、8、9）**。127/127 条 Stage 事件一致，10/10 个首块粒子 CSV 与 10/10 个完整视频的 SHA-256 均与历史原实验一致。此前历史源码 + Codex 的 1/10，主要由替换 Stage 模型及输出协议造成；不能归因于 Codex 接口调用失败。由于没有实时 Poe/Gemini，本次是**留存输出驱动的精确轨迹复现**，不是重新访问原服务的严格在线复现。当前源码的 C0 等价性仍未验证。

## 为什么上次不是严格复现

历史 C0 原实验来自源码 `53187e6ea8b69e9f830c10be0bc25757db5d2794`、Poe `gemini-2.5-flash` 的自由文本 Stage、GPU5 和当时的软件栈，报告 3/10。上轮用户批准的诊断改为本机 ChatGPT 登录的 Codex CLI `gpt-6-astra`/low，结构化 JSON schema Stage，物理 GPU2；历史源码得 1/10，当前源码得 0/10。模型、调用协议、硬件和依赖版本都不是原样，因此 1/10 或 0/10 从定义上不能叫原实验的严格复现。

关键差异在**控制内容**而不是连通性：历史源码 + Codex 的 185 次 Stage 查询全都成功且解析完整，没有鉴权、超时或 Stage 错误。原始 Poe/Gemini 日志只有 127 次查询，其中 20 次收到类似 `stage 0\nguidance:` 的不完整文本，历史解析器回退到 stage 1 / guidance ON；另外 11 次完整回复要求 guidance ON，所以原实验总计 31 次 ON。Codex 组 60 次 ON，且全是解析成功的输出。这些频次不能直接视作同分布调用，因为轨迹已分叉，但足以表明 Stage 输入到控制器的序列不同。

最早的可定位分叉发生在历史源码的 task 0：首个动作粒子 CSV 与原实验逐字节相同，第一次 Stage 都在第 24 步给出 stage 1 / guidance OFF；第 32 步的旧 Poe 回复给出 stage 2 / OFF，Codex 给出 stage 1 / ON。后者会切换 guidance 和后续动作，因此后面的调用数量、状态、成功率不再是配对轨迹。先前历史源码 1/10 与当前源码 0/10 的比较还受到另一层扰动：task 2 的同一 Stage 提示词及图像，在两轮 Codex 在线调用中得到不同 guidance；逐 episode 没有重置全局 Torch 随机流，后续任务首块粒子因此不同。0/10 本身不能证明当前源码退化。

作为辅助视觉核对，原始视频和旧源码 + Codex 视频的解码帧在第 0、24、31 帧平均像素差分别只有约 0.017、0.135、0.149（8-bit 通道尺度）；第 32 帧上升到约 5.185。旧实验未保存逐次 Stage 输入图像哈希，故不能证明两服务在第 32 步收到逐字节相同的图像；该帧差异与已记录的控制决策分叉一致。

## 这次如何隔离原因

先冻结[回放方案](../../../experiments/iteration_001_execution_intent/c0-trace-replay-20260925.md)和[输入/源码哈希清单](../../../artifacts/c0_trace_replay_20260925/manifest.json)，再在同一个旧源码工作树执行。命令继承原 `job_manifest.json` 的 Object-Swap 十任务顺序、种子 `[44,235,43,546,6,621,197,87,151,548]`、720 步、RDT Object EMA、EDS population 16/10 轮、非 CEM、absolute EEF RBF、多样性与 QD OFF 配置。保留上一轮已经核定的历史缓存副本。只将 Stage 服务替换为原实验 `stage_events.jsonl` 的 `raw_response` 逐次回放，仍走原解析器，包括 20 次不完整文本的历史回退行为。每次查询前核对 task、seed、步数、chunk、触发原因和先前 stage/guidance；首次不一致即停止，不能伪造完整分数。

回放在用户指定的物理 GPU2 顺序跑完 10 个主回合，用时 990.084 秒，即 0.275023 GPU 小时墙钟上界。没有重试、Stage 网络调用或 GPU 故障，GPU2 worker 已退出。[完整审计](../../../artifacts/c0_trace_replay_20260925/outputs/legacy/audit.json)为 `valid_full_replay: true`：

| 旧源码 + 在线 Codex | 1/10 | 9 | 更换 Stage 后的诊断，不是旧条件 |

回放不仅得到相同的成功任务：**127/127 条** Stage 记录在查询时点、触发、原文、解析结果和控制状态上匹配；**10/10 个**首块 EDS 粒子 CSV 的 SHA-256 匹配；**10/10 个**完整 MP4 视频的 SHA-256 匹配，成功任务结束步数分别为 120、314、285。视频逐字节相同意味着这些可见轨迹及成败判定完整对齐，证据强于只比较 3/10 分数。历史缓存原声明的运行目录已经不存在，因此无法重新哈希当时缓存本体；本次缓存副本的哈希已冻结，而精确视频与粒子匹配证明它没有造成这次轨迹差异。

## 归因和边界

本次控制变量实验表明：**在历史源码上，将 Stage 回复恢复为旧实验原文，足以恢复原来的整套轨迹和 3/10。** 因而此前 1/10 的主要可实证原因是 Codex/Gemini 在 Stage 决策和回复格式上的差异，而不是 Codex 连接故障，也不是当前 GPU2、权重加载、LIBERO 仿真或新版软件依赖阻止旧轨迹运行。GPU 与依赖版本仍与旧环境不同，但在这套固定回复下没有造成任何可见结果差异；不能据此推断它们在其他设置中永远无影响。

**严格的在线 Poe/Gemini 复现仍不可声称。** 现无可用 Poe 凭据，回放不能证明今天的在线 Gemini 会重复产生这些文本。旧源码 C0 的历史结果和当前 GPU2 执行基础已验证；**当前源码 C0 尚未在固定 Stage 回复条件下完成十任务配对验证**，所以也不能宣布新算法实验的当前代码基线已恢复。建议先做当前源码的同一十任务回复回放，检查 127 条事件和视频是否仍完全一致；若不一致，从首个动作/事件定位真正的源码差异，再进入 QD/ED 优化。现在未保护预算只剩 2 次尝试，无法在不调整既有保护额度/总额的情况下运行这 10 次；本报告没有动用验证或正式验收保护额度。

当前源码回放已完成代码和 CPU 配置预检，待审的具体预算与运行方案见[方案](../../../experiments/iteration_001_execution_intent/c0-current-trace-replay-budget-proposal-20260925.md)。它尚未消耗 GPU episode。

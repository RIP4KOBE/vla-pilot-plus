# Stage 完成、失败复查和 reward/ED 一致性修复

日期：2026-09-29。版本：`evidence_v1`。目录：原 GPU2 研究 worktree，未新建 worktree。

## 结论与适用范围

已经定位并修复三类控制逻辑问题。修复把视觉观察、阶段状态机和 ED 能力判断分开：模型报告事实，程序决定阶段，reward 能力与总开关共同决定是否执行 ED。采用显式版本，以便旧 C0 仍能走原路径；历史实验文件保持原样。

本轮交付是控制链修复与功能验证，不等于已经把十任务成功率恢复到 3/10，更不构成 5/10 的算法结果。环境自身的成功判定仍是任务成功率的依据。Stage 0 只是可撤销的视觉完成假设；控制器不读取环境 success 作为决策输入，也不会凭 Stage 0 提前结束环境。

## 原问题的证据

1. **完成判定被触发词和生成的阶段描述带偏。** 旧提示词把“gripper closed”解释为已经抓取，把“gripper opened”暗示为放置完成；靠近目标、reward 升高也能诱导关闭引导。它把动作命令当作环境事实。在最新完整 0/10 实验中，task3/step96 的回复宣称 BBQ 酱已在篮内，实际输入图片中酱瓶仍在篮外、篮子是空的。task7/step128 的牛奶也存在同类误判。历史缓存的阶段描述还可能沿用其他任务的物体名。
2. **关闭引导之后缺少稳定复查路径。** 旧 `_update_stage` 的 reward 上升/下降触发都依赖 `use_guidance=True`，没有真正实现注释所说的 periodic 检查。关闭 ED 后，policy 的归一化 reward 可能不再更新，旧值不能表示当前场景状态。只有新的夹爪事件等触发才能偶然再次查询。
3. **Stage 说“引导开启”与 reward 的实际能力脱节。** 最新实验里 9/10 个 Stage 2 函数返回常数零；这部分源自原 reward 模板明确的设计，不是九次 API 失败。301 个 guided chunks 中有 177 个 reward 为零。开着 ED 会继续承担搜索开销，却没有有效的质量信号。
4. **夹爪触发时序错误。** 新 chunk 开始时 `action_executed` 已清零，旧路径读取上一 chunk 的第一个动作，而非实际最后执行的命令；如果只执行了 chunk 的一部分，直接取 chunk 最后一个动作也不对。

因此，单靠更换 Poe 密钥不能修复这些程序和提示词层面的因果链。

## 本次实现

### 1. 模型只报告视觉事实

`core/stage_observation.py` 与 `vlm_query/stage_observation_v1.txt` 使用五字段 JSON：目标可见性、相对篮子的位置、是否被夹持、是否有支撑、可见证据。旧阶段描述中的控制指令与夹爪/reward 触发文字不送入观察提示词；初始图用于识别物体，当前图用于判断状态。

严格检查字段、枚举和重复键，不接受旧 `stage N / guidance yes` 作为新格式的替代输出。请求失败、不完整 JSON 或明确 length 截断会保留事件并报错，不能静默伪装成正常 Stage 1。底层网络重试沿用已验证的 transport launcher；不因模型答案不理想而重抽。

新格式初筛在旧 256-token 额度下出现一次不完整 JSON。新观察请求改为 2048，并记录 finish_reason。随后同一组 7 个输入全组重测，7/7 正常结束、7/7 合法解析；原初筛回复保留。旧 C0 的请求仍用 256。该结果支持新格式需要更充足的输出额度，不能把一次截断直接归咎于鉴权或所有 API 服务故障。

### 2. 完成需要跨时间确认，可以撤销

`core/stage_evidence.py:decide` 要求目标清晰可见、在篮内、未被夹持且得到支撑，才记一次完成证据。第一次先进入 Stage 2 等待复查；至少相隔 16 个环境步的第二次有效观察才接受 Stage 0。同一时间步重复调用不增加计数。中间出现未知或矛盾会打断确认链。

看见目标被夹持则进入 Stage 2；看见目标在篮外、未被夹持则回到 Stage 1。Stage 0 后仍继续复查；发现反证可以撤回完成状态。遮挡不等于已经完成，也不强行推断已经抓稳。

两次确认不能消除系统性视觉误判，因此它不是形式化成功证明。若两次都看错，仍可能误报；报告与评测只认可环境记录的 success。

### 3. 失败复查不依赖 ED 开关

启动时先做视觉检查。普通状态每 32 步复查，等待完成确认或不确定状态每 16 步复查，查询最小间隔 16 步。真实已执行夹爪命令的边沿可提前触发；间隔限制内发生的事件会保留到允许查询时。Stage 2/0 或因无可用 reward 而关闭 ED，都继续检查。

新版本不再把归一化 reward 的 Schmitt 阈值作为阶段决策触发依据。该量只是相对本阶段初始负 reward 的代理指标，不是成功概率；ED 关闭时日志把它记为不可用，避免把旧值作为当前证据。重新开启引导或切换阶段会重置 reward 基准和 chunk memory。

### 4. reward 能力决定有效引导

每个 chunk 使用当前 keypoints，在 CPU 上对聚合 reward 做确定性的静止/移动候选轨迹检查。缺失函数、错误输出、非有限数、非确定输出、候选间常数输出都会关闭 ED，并记录原因；一个最优位置恰好得零分不会被误判为常数。多函数相消也按聚合结果检查。

有效开关为：总开关允许 AND 控制器请求引导 AND 当前阶段 reward 有区分能力 AND 非完成状态。函数检查不消耗主 Torch/NumPy/Python 随机流。它只检查数值能力，不证明目标索引、符号、尺度或任务语义一定正确，也不能证明有限探针覆盖所有未来输入。

实际现有 20 个函数：10 个 Stage 1 全部保留；9 个常数 Stage 2 关闭；task7 牛奶的非零 Stage 2 保留。模型不能再用一句 guidance=yes 覆盖这个检查。Stage 2 没有有效 reward 时，底层 RDT 仍执行自然动作，在线观察继续运行。

## 验证与结果

- CPU：178 项测试通过，包含完成确认/撤销、未知与遮挡、节流保留事件、ED 关闭后复查恢复、总开关、非有限/常数/相消 reward、部分 chunk 夹爪命令、请求捕获与旧路径兼容检查。
- 真实保存图片：最终配置 7/7 合法观察，7 次 HTTP 请求，全部 finish_reason=stop；BBQ/牛奶两处明确假完成均回到“篮外，重新抓取”。历史橙汁 step248 画面识别为篮内，进入第一次确认。两个抓取画面因遮挡仍不确定。这是有针对性的定性诊断，不是独立测试集准确率。
- 原 C0 兼容：默认仍为 `legacy`，冻结前后的旧 `_update_stage` 主体 AST 一致；新请求与 parser 仅在 `evidence_v1` 生效。此次没有重新跑一组旧 C0 GPU 十任务，不能把代码兼容检查写成又一次 3/10 复现。
- GPU2：完整 720 步，**任务失败 0/1**；功能审计通过。90 个 chunk 中 42 个 ED 开启、48 个关闭；逐 chunk 开关与实际 ED 指标记录完全对应，零 reward ED 次数为 0。38 次在线观察全部合法，其中 20 次在原有引导关闭状态下触发；44 次 HTTP 尝试含 6 次 SDK 网络重试，无最终接口失败。耗时 900.16 秒（约 15 分钟，含加载），GPU2 已释放。

GPU 功能回合固定 task3/seed546、720 步上限、C0 RDT/ED 参数、Gemini-3-Flash；复用上轮为 task3 新生成的 reward 以隔离本次控制修复。单任务新进程的 policy RNG 不等于原十任务连续执行到 task3 的 RNG，因此不作成对成功率结论。该回合保存逐 chunk 决策、真实 HTTP 输入和完整视频。

### 完整回合说明

6 次 Stage 2 → Stage 1 恢复分别发生在 step 104、280、344、608、656、696；随后有效 reward 的 ED 重新开启。step64 首次看到目标被夹持后关闭常数零 Stage 2 ED；step104 看到目标在篮外、脱离夹爪后恢复抓取。视频显示抓取/运输过程中仍有反复掉落。

本回合没有产生 Stage 0，也没有成功放置；因此在线“真完成的两次确认”分支尚未在成功 rollout 中验证，该分支当前的证据来自 CPU 场景测试与保存图片观察。不能把“未误报完成”写成任务完成能力已经恢复。重复闭环中遮挡/未知观察仍有 17 次；阶段更保守的代价及底层抓持不稳，需要下一轮固定条件对照。

## 使用与后续实验建议

在一个新的 C0 派生配置上加入 `+stage_controller=evidence_v1`。预设会启用新控制器及 16/32/16 步间隔，保留每回合 50 次查询限制；不要把旧 manifest 中显式的 `+main.stage_min_query_gap_steps=0` 一起带入。完整可运行命令与冻结源码见本轮 smoke manifest。只支持显式选择的两阶段 LIBERO pick/place 与 OpenAI-compatible 观察接口；不能自动套用到其他多阶段操作或 Codex CLI。

下一步应先冻结这一控制版本，用各任务对应的同一套已生成 reward，完整跑十任务检查成功率、失败复查恢复次数、无效 ED 次数、查询/运行成本。这样才能判断控制修复的净效果。若遮挡使“实际已抓住”长期无法确认，应检查相邻帧运动证据或相机视角；若进入正确阶段仍抓取/放置失败，再分析 reward 的目标语义、尺度和动作引导强度。达到稳定基线后再开展 QD/ED 搜索机制迭代。

# 更换 Poe 凭据后仍为 0/10：控制机制诊断

本报告在上一份十任务结果报告基础上，继续核对源码、动作段计算计数、候选粒子哈希和原始图像，并执行 CPU 机制探测。未新增 GPU 回合或在线 API 请求，未改变已经完成的实验代码/结果。

## 核心结论

Poe 的鉴权和传输已经恢复，但基线不是由一个 API 地址决定。当前系统把模型的 Stage/guidance 回复直接用于启停整个 ED 搜索，又缺少关闭后的可靠恢复路径；历史缓存没有有效的第二阶段评分，触发信息还有动作时序错位。新模型的错误判断进入这些控制分支后，会让很长一段执行退回单候选 RDT。与此同时，历史格式回退和跨任务随机数耦合使旧 3/10 无法直接视为新模型十任务的严格配对参考。

这些大多是历史设计中已有的限制，而非本次换 Poe 凭据引入的新回归。它们的存在和被实际执行已有代码/日志证据；每一项单独造成多少成功率损失，仍需要闭环消融。不能把全部 0/10 归因于单一因素，也不能承诺修某一项必然达到 3/10。

## 1. 已排除与尚未排除的因素

本轮 181/181 次 Stage 查询完成并成功解析，190 次 HTTP 尝试中 9 次 SDK 重试恢复；十个任务完整执行、结果与视频一致。reward 生成 API 调用计数为零。九个冻结关键源码文件与六个历史缓存文件运行前后不变。此前完整历史回复回放在当前源码恢复 3/10，本轮 task 0 真实在线运行的整段视频也与历史逐字节相同。

因此没有证据支持“这次是鉴权、实验提前停止、缓存被替换，或当前执行链普遍无法还原历史”这一解释。恢复的是 Poe 接入；用户批准使用的是 Gemini-3-Flash，历史是 Gemini-2.5-Flash，模型条件并不相同。但仅指出换了模型还不足以解释控制如何失败，下文给出实际机制。

## 2. guidance=no 关闭的是整个 ED 路径

`core/rdt_policy_steer.py:1517` 开始的 `select_action()` 分支显示：开启 guidance 时调用 `_predict_guided()`；关闭时直接调用 `_predict_unguided(..., B=1)`。因此它不是只调低一点引导强度，而是停止多候选 ED 搜索。QD 若挂在该 ED 路径，也不会在关闭时运行。本轮 C0 本来就没有启用 QD archive。

本轮实际计数：

| 实际执行模式 | 动作段数 | 占全部 900 段 |
| --- | ---: | ---: |
| stage 1 / guidance on，即 ED 生效 | 106 | 11.8% |
| stage 1 / guidance off | 23 | 2.6% |
| stage 2 / guidance off | 304 | 33.8% |
| stage 0 / guidance off | 467 | 51.9% |
| 全部 unguided 单候选 RDT | **794** | **88.2%** |

task 0、1、4、6、8 均只有第 0、8、16 步三个 ED 动作段，第 24 步关闭后，剩余 87/90 个动作段一直没有恢复 ED。只优化当前 gate 内部的 QD/ED，无法直接改变这些被绕开的动作段；当然，早期更好的动作仍可能影响后续轨迹，不能据此说 QD 完全无效。

## 3. 关闭 guidance 后，失败恢复存在缺口

`main.py:1290` 的 reward 上穿/下穿触发都要求 `state['use_guidance']` 为真。实际实现只处理夹爪命令符号变化和 reward 阈值穿越，没有注释所提到的周期复查。只要 guidance 已关闭，即使另一个观测器给出 reward 从 0.95 跌至 0.10，也不会因此重新查询 Stage。

CPU 探测直接执行源码中的 `_update_stage()`，其余状态相同：

| 输入条件 | Stage 查询数 |
| --- | ---: |
| guidance on，reward 0.95→0.10，夹爪命令不变 | 1 |
| guidance off，同样 reward 下降、同样夹爪命令 | **0** |

而真实运行还有第二层限制：归一化 reward 来自上次 ED 候选评分；进入 unguided 路径后没有重新评分。task 8 第 24、32、152 步日志中的数值均为 `0.9377510040160643`，不是连续测得物体已经成功放置。

task 8 的具体轨迹为：第 24 步关闭 guidance，第 32 步进入 stage 2/off，第 152 步误判 stage 0/off，随后直到第 720 步没有新的 Stage 查询，也没有 ED。当前图像可见篮筐为空、目标在篮外右侧。**一次错误关停之后，系统没有可靠的失败复查路径。** stage 0 本身不立即终止仿真，环境仍运行至失败，因此不能将该问题描述为“程序提前结束了任务”。

## 4. 触发词有时不对应最近实际执行的夹爪命令

`main.py:1671` 以 `_get_gripper_value(action_chunk, action_executed)` 构造 Stage 触发。新动作段边界处，`action_executed` 已在上一循环中重置为 0，所以读取的是**上一动作段的第一个命令**；程序虽然记录了 `previous_executed_gripper_command`，这里却没有使用它。

本轮 181/181 个记录的 `gripper_value_used` 等于 `first_gripper_value`；其中 **19 次**首尾命令相反。例如 task 9 第 72 步：使用值为 +1，提示“gripper closed”，但上一段最后执行的命令是 -1（张开）。图像来自执行完上一段之后，文本触发和图像时刻可能错位。

CPU 探测用一个“前七步张开、最后一步闭合”的动作段验证，当前边界读取为张开，而最近执行命令为闭合。即使改为正确的最后命令，它仍只是命令，不是“确实抓住目标”的物理或视觉证据。

从历史提交 `53187e6e...` 提取代码，确认同样的首命令读取和 guidance 条件门控已存在；这是继承的实现问题，不能说是接入 Codex 时新增的 bug。19 次是本次已记录查询中的首尾矛盾数，不代表已统计全部未触发查询的遗漏。

## 5. Stage 提示词与缓存内容在鼓励未经验证的跳转

原提示词 `vlm_query/stage_template.txt:16` 将“gripper closed”解释为机器人已抓住东西；`:49` 将“已接近目标”和“已经抓住”都列为关闭 guidance 的理由。缓存 `output_raw.txt` 又明确写着第二阶段不需要 guidance。因此部分回复是在遵循输入中的不可靠先验，而非单纯由模型视觉能力决定。

最明确的反例是 task 9 第 88 步：模型原文已经承认 orange juice 在篮外、没有放入篮筐，却仍返回 stage 0/no，理由是夹爪已释放、一次尝试已经结束、没有定义纠正阶段。这里既有任务完成概念错误，也暴露出状态定义中缺少失败恢复。

task 1 第 64 步、task 8 第 152 步则在篮筐为空时宣称放置成功。当前系统把这些回复直接应用，没有独立的“目标是否确实在篮内”证据约束。

历史旧 Poe 也有错误 Stage 判断；此前 Codex E 将未确认抓取时的 stage 1 guidance 保持开启，十任务仍为 0/10。故“换更强模型”或“始终开启 stage 1”都不是已经证明有效的修复。

## 6. reward 缓存可复用，不等于它覆盖整个任务

历史 stage 1 reward 实际是末端候选轨迹到 keypoint 0 的加权负平方距离：它衡量接近目标，不直接判断夹持、稳定搬运、正确释放或是否落入篮筐。归一化值使用 `1 - reward / stage_init_reward`，属于相对评分改善，**80% 不是抓取完成概率或任务完成度**。评分针对候选轨迹，亦不等同于已经实现的物理状态。

历史 stage 2 函数则是：

```python
def stage2_guidance(keypoints, action_sequence):
    return torch.tensor(0.0, device=action_sequence.device)
```

CPU 探测将末端候选分别置于目标、目标与篮筐之间、篮筐，stage 2 的三个评分全部为零。因此它没有为“更接近篮筐、更好的放置”提供质量排序。即使强制 stage 2 开启 ED/QD，也不会凭空产生有意义的放置质量信号。多样性仍可能产生不同候选，但不能称作 reward 对放置质量进行了优化。

更准确的结论是：缓存文件完整、可用于复现；第一阶段局部接近目标的 reward 可继续作为研究控制条件；**若想优化完整抓取—放置过程，第二阶段 reward 需要单独设计与验证**。此前只强调“缓存没有损坏”，不足以说明其研究适用范围。

另外，缓存文字把各任务都称为 alphabet soup，但数值函数使用的是动态映射的 keypoint 0，而实际指令与物体映射正确。它是应清理的文本问题；既有 Codex 单变量名称修正几乎不改变决策，没有依据将全部失败归咎于这一点。

## 7. 为什么历史能有 3/10

历史得到的 3/10 是真实可回放结果，但实际协议包含 **20/127 次格式异常回退**。缺少 guidance 值时，旧解析器会回退为 stage 1/on，相当于重新介入接近目标。这 20 次占历史 31 次 stage 1/on 的大部分；其中历史成功的 task 8 有 2 次、task 9 有 4 次格式回退。不能以此推断“所有成功均来自回退”，但其控制影响不能忽略。

新旧精确相同输入上的首次分歧在 task 1 第 64 步：旧回复未给完整 guidance 值，回退 stage 1/on；新模型完整但错误地返回 stage 0/off。本轮该任务只有 3 个 guided chunks，而历史回放为 12 个。

随后跨任务随机流进一步放大差异。对每个任务第一个候选粒子 CSV 的 SHA 比对结果为：

```text
task 0  task 1  task 2  task 3  task 4  task 5  task 6  task 7  task 8  task 9
 相同    相同    不同    不同    不同    不同    不同    不同    不同    不同
```

原因是环境种子被固定，但策略 Torch 随机流仍跨 episode 连续使用；ED 的多候选采样和 unguided 的单候选采样消耗不同。于是 task 1 的变化影响 task 2 以后的初始候选。旧三个成功任务本轮已经不是相同的初始策略随机状态，不能把结果差额全解释成“同一状态下新模型不如旧模型”。

| 历史成功任务 | 历史 guided/全部动作段 | 本轮 guided/全部动作段 | 解释边界 |
| --- | ---: | ---: | --- |
| 3 / bbq sauce | 4/15 | 18/90 | 本轮引导更多仍失败，证明不能只追求引导数量 |
| 8 / chocolate pudding | 8/40 | 3/90 | 本轮第 24 步后不再开启 ED；历史有两次解析回退 |
| 9 / orange juice | 9/36 | 7/90 | 本轮出现“承认篮外仍判完成”；历史有四次解析回退 |

历史成功任务会提前结束，分母不同；该表用于描述实际执行，不能据比例直接估计因果效应。

## 8. 下一步应如何把研究带回可迭代状态

优先处理确定的机制缺口，而非再换一次 API 或直接扫 QD 参数：

1. **修正输入时序和恢复机制。** 明确区分最近执行命令、夹爪观测和真实抓取证据；关闭引导时仍有有界的状态复查；reward 监视值若不更新，要标记为过期，不能冒充当前状态。保留原协议作为旧版本。
2. **将物理状态判断与控制决策分开。** 模型报告目标位置、抓取/释放证据和不确定性，由明确规则决定 stage/guidance；明确“篮外释放是失败/恢复状态”，不是任务完成。使用当前/近期视觉输入，仿真成功真值只作离线诊断，不暗中输入在线算法。
3. **隔离每个任务的策略随机流。** 新参考 C0 和修订版都使用同一逐 episode 种子协议。它不能保证两种算法在每个后续动作段消耗完全相同的随机数，但至少避免前一个任务改变后一个任务的初始候选。
4. **单独补充和验证第二阶段质量信号。** 如要优化搬运/放置，先让 reward 能区分明显好坏候选，并保持任务/物体映射正确；不要将此改动混进只验证 API 或触发时序的对照。

最小闭环定位矩阵可以是同一新随机数协议下的三个十任务条件：A 保留旧控制规则；B 只修正触发时序与关闭后的复查；C 在 B 上加入明确的抓取/完成/失败恢复证据规则。第一阶段缓存及第二阶段零 reward 在这三组中保持不变，用于分离控制问题。若运输/放置仍是主要失败，再将非零第二阶段 reward 作为独立 D 条件，并相应定义何时启用该阶段引导。

检查的不仅是总成功率，还包括提前关闭引导、错误完成判定、失败后能否恢复、ED 实际生效动作段及三个原成功任务的失效位置。所有合法失败保留，不靠重试挑出 3/10。

可以立即开展上述 Stage 机制修复与离线 ED/QD 单元验证；在在线控制条件未稳定之前，不应把混杂后的成功率变化归因于 QD/ED 本体。此前“先恢复在线基线再比较算法”的顺序仍合理，但恢复对象应是明确、可验证的控制协议，而不是 Poe 这个接入名称。

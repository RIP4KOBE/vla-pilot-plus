# Stage 诊断修复与后续实验准备

用户要求继续后，先完成CPU侧诊断修复。N1U的关闭结论和所有原始结果不变，
尚未派发新的GPU2实验回合。

源码提交：`337196e8672a2309b06d221c9f3436bc81cf9083`。

新增脱敏诊断覆盖顶层error、error item、turn.failed和有长度上限的stderr，
记录文本标记、明确HTTP状态码和摘要指纹，不保存原始服务端错误/凭据。
增加用户提示与原PNG的指纹，以便后续区分输入是否变化；该指纹不代表
捕获了CLI内置系统提示的全部内容。所有诊断仅供观察，不改变调用接受规则。

153项CPU检查通过（6.63秒），包括错误条目与stderr的脱敏、180秒超时
清理、完整用量保留、已失败调用仍拒绝、stderr标记不会误判正常响应、
诊断读取异常不会破坏原判定，以及提示/图像顺序不变。

历史故障未复现，底层根因和长时间稳定性仍未证明。

本地CLI的features查询显示旧responses_websockets开关已经标记为removed，
因此没有依据去启用或禁用这些旧开关作为修复。Stage已有的
unbounded_connection_retries禁用设置保持不变。未修改模型、提示词、
超时、成功校验或算法机制，未追加更多探针来追求一个有利的成功率。

共享预算核查发现，之前的分组调拨只同步了GPU2工作树，另一工作树仍
使用旧分组额度并继续派发N4。原始消耗必须保留，先前“还差2次”的快照
已不适用。按用户既有GPU2优先授权，已于04:52:25 UTC在GPU3当前回合
完整结束后暂停其后续队列；没有中断GPU回合。两边预算状态已同步回
先前获批的分组上限，实际baseline超支2次保留、不改写。当前共享114次，
16.0814 GPU小时；总240次内扣除验证/正式保护后实际仅余26次开发/恢复。
预算与停止规则的下一次修改
需要共同、明确的准入依据，不能只改一个工作树的状态缓存。

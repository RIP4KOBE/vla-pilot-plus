这样可以直接检验将要发布的整合代码是否保持 EDS 行为，并避免先在研究环境测通、迁移后才暴露依赖或接口差异。

**三、从准备到 main 的具体步骤**

**步骤 A：核验并固定来源。**

在来源工作树对照已验收证据，固定源码、配置、提示词、任务与初始化、模型/资产、环境依赖。记录已跟踪修改及必要未跟踪文件的内容哈希，形成可重建的来源记录。原始结果不改写。

不预先重复一整轮来源在线评测；只有发现依据不足、源码漂移或迁移差异时，才增加有明确问题的来源诊断。API 探测与 GPU 预检独立进行，避免改变正式回合 RNG。

**步骤 B：在现有主目录建立整合分支。**

实施时先核对远端 main，选定明确起点，再在现有主目录创建 `codex/rdt-steering-integration`。保护当前未提交文件，不使用强制重置或全量清理。

此后阶段 2–5 的代码开发、测试和提交均在这个整合分支进行。运行过程中不切分支、不修改受测源码；同一目录不能供多人同时切换不同分支。

**步骤 C：按清单迁移 EDS 及完整依赖。**

以 main 的当前结构为基础，选择性引入 EDS、Stage/reward 修复、必要 QD 依赖、输入/资产适配、配置与测试；处理与现有 VLS 和其他策略的兼容性。使用算法或职责名称整理公共入口。

迁移以已核验文件内容为准。对提交边界清晰、依赖明确的修改可以采用 Git 提交迁移；未提交实现必须按文件纳入并形成新的整合提交。不会把整个研究分支和所有历史实验目录直接合入。

运行脚本、实际 import 与运行时源码哈希必须对应整合目录。模型和大资产可从配置指定的共享位置读取并校验，但不能靠导入来源工作树的 Python 文件来“通过”验收。

**步骤 D：在整合代码上完成 EDS 十任务验收。**

先完成相关 CPU 回归与离线一致性检查，再固定受测提交、配置、依赖与初始化证据。在 GPU2 完整执行十任务，使用当前 Codex 在线机制。

以选定协议下已验收 EDS 的 3/10 为性能参照；完整报告有效性、逐任务结果与差异。失败后按问题定位，不替换合法失败或拼接成绩。

源码来自整合分支；日志、视频和结果仍写入已有实验管理区域。每个结果记录对应源码与配置身份，不能由输出目录位置推断代码来源。

**步骤 E：统一三模式并建立对照。**

在同一整合分支接入 VLS、EDS、EDS+QD 的公共 selector、接口契约和审计。先核对 EDS 是否保持已验收语义，再运行 VLS 与 EDS+QD 各十任务。

若接口适配改变 EDS 的科学条件，追加共同协议下 EDS 十任务作为新的对照；若源码改变但预期语义不变，也必须通过相关行为检查，根据未解决风险决定是否需要在线重验。

通常为 30 个主回合，需重建 EDS 对照则为 40 个。各次结果保留真实代码与配置来源，不因位于同一整合分支就视为完全相同设置。

“完整成功”在此表示：EDS 迁移及性能状态明确，三模式有效运行并形成可审计结果。EDS+QD 超过 EDS、达到 5/10 或实现递归改进属于后续研究目标，不是研究框架首次合入的前提。

**步骤 F：形成可评审的整合交付。**

完成 README、环境与资产说明、三模式运行命令、结果表、已知限制和来源索引。仅暂存纳入整合的文件，不使用无筛选的全量暂存；密钥、私人环境文件、模型权重及大规模原始产物不混入代码提交。

提交按依赖/资产、EDS 与控制修复、公共入口、三模式接口、测试与文档等单元组织。科学行为变化与纯命名/路径变化分开，使审核和回退可定位。

**步骤 G：更新到最终目标 main，检查实际待合并代码。**

最终合并前核对远端 main 是否有新提交。若 main 已前进，先把这些变化纳入整合分支，在整合分支处理冲突并检查兼容性。根据变化重跑相关检查；若影响算法、控制、模型输入、RNG 或任务条件，需进行相应在线验收。

已经通过评测的旧分支提交不能自动担保冲突解决后的代码。只有最终待合并内容对应已验收实现，才进入合入步骤。

**步骤 H：合入并发布共同基准。**

推荐推送整合分支并创建面向 main 的 PR，提交内容、验收报告与限制一起评审；通过后使用保留整合提交的 merge commit。若团队采用本地集成，可在同步后的 main 使用 `git merge --no-ff codex/rdt-steering-integration`，随后按团队远端流程发布。

上述是拟定的发布流程，本轮尚未执行 push、创建 PR 或 merge。

合并后核对 main 的运行时源码与已验收代码一致，进行必要的入口冒烟检查。合并只改变 Git 历史且代码内容未变时，不自动重复全部在线回合；发现实际差异则针对影响补验。

README 填写实际来源、整合分支、工作树与受测提交。实际 merge commit 在产生后补入来源记录，可通过后续文档提交完成。为首个团队基准保留明确的提交或发布标签，方便以后回溯。

**四、合作者如何从 main 继续开发**

团队使用发布后的同一个 main 提交作为研究起点。每位合作者在自己的 clone 或独立工作目录中同步 main，建立自己的功能分支；不要多人共用当前整合目录切换分支。本次不新增工作树的安排不要求所有合作者共享同一磁盘 checkout。

分支按改动职责命名，例如：

- `codex/qd-descriptor`：行为描述符与网格。
- `codex/qd-parent-selection`：父代与探索分配。
- `codex/qd-execution-feedback`：执行反馈和受控记忆。
- `codex/steering-evaluation`：共同评测与审计。

这些只是后续候选分支名，尚未创建。公共方法名仍保持 `vls`、`eds`、`eds_qd`；同一方法的研究变化通过机制参数和可追溯的运行记录区分。

每位合作者遵循相同流程：

1. 从共同 main 派生功能分支，明确只改变哪些机制、哪些外层条件保持不变。
2. 保留冻结的 EDS 配置；新候选采用独立配置或显式参数，不覆盖已有基准成绩。
3. 完成必要单元/回归检查，再按共同协议运行候选与必要对照，保存代码、配置、seed、实际计算量和逐任务结果。
4. PR 说明问题、机制变化、对照证据和限制；改动 Stage/reward/初始化等共享条件时，明确所有受影响方法。
5. 主线更新先在自己的分支合并并解决冲突，验证最终候选，再由评审合入 main。

研发可以并行，GPU2 的整套评测按统一队列串行安排，避免资源竞争影响结果。需要使用其他设备时记录设备和环境差异。

后续 EDS+QD 的候选先在开发任务验证，再用冻结的独立评测判断是否形成新推荐配置。十个反复调参任务上的提升不单独作为泛化结论；现有 EDS 仍作为固定参照可运行。

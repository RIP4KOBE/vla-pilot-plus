# RDT+EDS Evaluation Protocol

Date: 2026-06-11

Worktree: `.worktrees/feat/rdt_ed_steering_integration`

Scope: evaluate whether the RDT+EDS steering mechanism is correctly deployed and algorithmically effective after implementing the integration design in `docs/01_specs/2026-06-06-rdt-eds-guidance-integration-design.md`.

This protocol is restricted to:

- policy: RDT only
- in-distribution suite: `libero_object`
- OOD setting: LIBERO-PRO perturbations of `libero_object`
- methods: unguided RDT and RDT+EDS variants/ablations only

Out of scope for this protocol:

- RDT+VLS comparison
- PI05 comparison
- `libero_spatial`, `libero_goal`, `libero_10`
- base-OOD terminology or base-OOD evaluation
- using prior bad OOD results as evidence against EDS

## 1. Motivation

The purpose of this evaluation is not to reinterpret previous OOD runs. Those runs are excluded from this protocol because their poor results were caused by incorrect checkpoint loading / checkpoint-evaluation mismatch. They are not treated as evidence about EDS algorithm validity.

The target question is narrower and cleaner:

1. After deploying EDS according to `2026-06-06-rdt-eds-guidance-integration-design.md`, does RDT actually enter the EDS path and execute the intended population optimization loop?
2. Under a correctly loaded RDT checkpoint for LIBERO-Object, does EDS improve reward, target progress, and task behavior on `libero_object`?
3. After LIBERO-PRO perturbations are correctly installed and generated, does EDS remain effective under perturbation OOD on `libero_object_*` suites?

Task success rate is important, but it is not enough. The evaluation must also prove that EDS is not just unguided denoising with extra latency. The required evidence includes route counters, population scoring, resampling, renoise, rollout, best-particle selection, zero-reward ablation behavior, and trajectory/reward improvement.

## 2. Required Preflight

Before any EDS evaluation, run a preflight that verifies the environment, checkpoint, and LIBERO-PRO status.

### 2.1 RDT Checkpoint Preflight

Required checks:

| Check | Pass criterion |
| --- | --- |
| RDT checkpoint path | points to the intended LIBERO-Object checkpoint |
| RDT weight file | resolved weight path exists and matches expected variant |
| RDT config | `state_token_dim == 128`, `pred_horizon == 64`, LIBERO active action slots are valid |
| text encoder | T5 embedding is nonzero for `libero_object` instructions |
| vision encoder | SigLIP image encoding succeeds with current observation images |
| action decode | selected RDT action slots decode to `(1, H, 7)` LIBERO raw actions |
| environment | `libero_object` reset, step, render, and success check work |

Preflight failure blocks all EDS effectiveness claims.

### 2.2 LIBERO-PRO Preflight

OOD evaluation in this protocol means LIBERO-PRO perturbations of `libero_object`. If any required file or package is missing, it must be installed or restored before OOD evaluation.

Required files:

```text
third_party/libero_pro/perturbation.py
third_party/libero_pro/evaluation_config.yaml
third_party/libero_pro/<required ood_task_configs>
```

Required install state:

```bash
cd third_party/libero_pro
pip install -e .
```

Required runtime checks:

| Check | Pass criterion |
| --- | --- |
| `PERTURBATION_AVAILABLE` | true in `core.env_adapters.libero_adapter` |
| `evaluation_config.yaml` | exists and loads |
| generated BDDL/init files | exist for each requested `libero_object_*` perturbation |
| benchmark key | perturbed suite can be loaded by the LIBERO benchmark |
| language-changing perturbation | `_lan` and `_task` read instruction from perturbed BDDL |

If LIBERO-PRO is missing, the evaluation owner must install/restore it and re-run preflight. OOD jobs must not silently fall back to base `libero_object`.

## 4. Evaluation Principles

1. Ignore prior bad OOD runs caused by wrong checkpoint loading.
2. Evaluate RDT+EDS only; do not compare against RDT+VLS in this protocol.
3. Use `libero_object` as the only base task suite.
4. Define OOD exclusively as LIBERO-PRO perturbations of `libero_object`.
5. Keep deployment correctness and algorithm effectiveness as separate gates.
6. Require zero-reward, shuffled-keypoint, and inverted-reward ablations before claiming EDS effectiveness.
7. Report reward/progress metrics even when sparse task success is low.
8. Treat missing LIBERO-PRO as an environment setup blocker to resolve, not as a reason to skip OOD evaluation.

## 5. Evaluation Levels

### Level 0: Deployment Correctness

Purpose: prove that RDT+EDS is wired correctly and actually executes the intended EDS algorithmic loop.

Required checks:

| Check | Metric | Pass criterion |
| --- | --- | --- |
| EDS route | `eds_enter_count` | > 0 for every guided chunk |
| Config propagation | `population_size`, `cem_iters`, `use_cem`, `temperature`, `num_elites` | exactly match `main.eds_config` |
| Population shape | `population_shape` | `(population_size, 64, 128)` |
| Score shape | `score_shape` | `(population_size,)` |
| Score finite | `score_nonfinite_count` | 0 |
| Initial scoring | `initial_score_call_count` | 1 before first resample |
| Resampling count | `resample_count` | equals `cem_iters` |
| Renoise count | `renoise_count` | equals `cem_iters` |
| Rollout count | `rollout_count` | equals `cem_iters` |
| Post-rollout scoring | `score_call_count` | equals `1 + cem_iters` |
| Best selection | `selected_idx` | equals `argmin(final_costs)` |
| Action mask | `action_mask_violation_max` | <= `1e-6` |
| Zero-reward no-op behavior | zero-reward ablation metrics | no systematic improvement; selection behaves like tie/random |

Minimum deployment gate:

```text
EDS loop entered
+ score/resample/renoise/rollout counts match cem_iters
+ population scores finite
+ selected particle is actually best-cost particle
+ zero-reward ablation behaves like no-op / random selection
```

Recommended Level-0 tests:

1. CPU/mock route test: `guidance_type=eds` calls `_eds_guided_denoise_loop()`.
2. CPU/mock shape test: EDS returns `(1, 64, 128)` selected particle and stores candidate population.
3. Synthetic score test: known costs select the known best particle.
4. Counter test: with `cem_iters=10`, observe 1 initial score, 10 resamples, 10 renoises, 10 rollouts, 11 total score calls.
5. Zero-reward test: all scores equal; no deterministic reward improvement should be reported.

### Level 1: Offline Algorithm Mechanism Probe

Purpose: prove EDS improves candidate actions under controlled rewards before spending full rollout time.

Protocol:

1. Freeze one real `libero_object` observation.
2. Freeze keypoints from that observation.
3. Use deterministic seeds.
4. Run EDS with synthetic rewards and save the initial population, all per-iteration populations, costs, rewards, selected particle, and decoded EEF trajectories.
5. Compare normal reward against zero reward, shuffled keypoints, and inverted reward.

Synthetic rewards:

| Reward | Definition | Expected behavior |
| --- | --- | --- |
| Move to fixed keypoint | `-distance(final_eef, target_keypoint)` | selected distance decreases |
| Positive-X motion | final EEF x displacement | selected trajectory moves +X |
| Negative-X motion | negative final EEF x displacement | selected trajectory moves -X |
| Zero reward | always 0 | no systematic improvement |
| Shuffled keypoints | normal reward with permuted keypoint ids | worse than normal |
| Inverted reward | distance to target instead of negative distance | worse or opposite movement |

Metrics:

| Metric | Formula | Meaning |
| --- | --- | --- |
| `initial_best_reward` | max reward before EDS iterations | best starting candidate |
| `final_best_reward` | max reward after final iteration | best optimized candidate |
| `best_reward_delta` | `final_best_reward - initial_best_reward` | reward improvement |
| `target_distance_before` | distance for initial best candidate | starting geometric progress |
| `target_distance_after` | distance for selected candidate | final geometric progress |
| `target_distance_delta` | `target_distance_before - target_distance_after` | positive means closer |
| `selected_advantage` | `selected_reward - final_mean_reward` | selection quality |
| `reward_spread` | `max_reward - mean_reward` | whether scoring separates candidates |
| `score_entropy` | entropy of resampling probabilities | selection sharpness |
| `population_diversity` | mean pairwise trajectory distance | diversity/collapse |
| `best_idx_nonzero_rate` | fraction of chunks where `best_idx != 0` | proves not defaulting to particle 0 |

Level-1 mechanism gate:

```text
In >=70% guided chunks:
  final_best_reward > initial_best_reward
  OR target_distance_after < target_distance_before

+ normal reward outperforms zero reward
+ normal reward outperforms shuffled keypoints
+ normal reward outperforms inverted reward
+ selected particle reward is above final population mean in >=70% of chunks
```

If this gate fails, online SR should not be used to claim EDS effectiveness.

### Level 2: Online `libero_object` Smoke Test

Purpose: prove EDS runs through the real episode loop on `libero_object`, with real keypoints, real generated guidance functions, real RDT actions, and real `env.step()`.

Methods:

1. RDT unguided
2. RDT+EDS normal reward
3. RDT+EDS zero reward
4. RDT+EDS shuffled keypoints
5. RDT+EDS inverted reward

Run size:

| Stage | Episodes per method | Purpose |
| --- | ---: | --- |
| Smoke | 3 | catch runtime and metric issues |
| Minimum | 10 | first quantitative comparison |

Metrics:

| Metric | Purpose |
| --- | --- |
| `episode_success` | sparse LIBERO task outcome |
| `time_to_success` | efficiency when successful |
| `max_progress` | partial behavior when unsuccessful |
| `mean_selected_reward` | reward quality during episode |
| `mean_reward_delta_per_chunk` | online EDS optimization effect |
| `target_distance_start/end/min` | whether selected trajectories approach target |
| `failure_type` | manual failure diagnosis |
| `select_action_latency_p50/p95` | RDT+EDS policy latency |
| `eds_loop_latency_p50/p95` | EDS-only latency |
| `wall_clock_per_episode` | end-to-end runtime |

Level-2 smoke gate:

```text
EDS completes all real episodes without runtime errors
+ EDS reaches env.step() and writes videos/results
+ real keypoints and real guidance functions are used
+ normal EDS improves reward/progress over zero-reward EDS
+ no numerical guardrail failures
```

### Level 3: `libero_object` Success Evaluation

Purpose: judge whether EDS improves or preserves task performance on the base `libero_object` suite under the correct RDT checkpoint.

Methods:

| Method | Purpose |
| --- | --- |
| RDT unguided | baseline policy capability |
| RDT+EDS p16 c10 | minimum accepted EDS config |
| RDT+EDS p16 c20 | iteration sensitivity |
| RDT+EDS p32 c10 | population sensitivity |
| RDT+EDS p32 c20 | stronger but expensive setting |
| RDT+EDS p32 c10 CEM | CEM vs probability resampling |
| RDT+EDS zero reward | steering ablation |
| RDT+EDS shuffled keypoints | keypoint dependency ablation |
| RDT+EDS inverted reward | reward sign sanity |

Run sizes:

| Stage | Episodes per method | Use |
| --- | ---: | --- |
| Minimum | 10 | first pass |
| Target | 50 | lower-variance SR estimate |

Primary metrics:

| Metric | Definition |
| --- | --- |
| `success_count` | successful episodes / total episodes |
| `success_rate` | success percentage |
| `wilson_ci_95` | confidence interval for SR |
| `delta_vs_unguided` | EDS SR - unguided RDT SR |
| `normal_vs_zero_delta` | normal EDS SR/progress - zero-reward EDS SR/progress |
| `normal_vs_shuffled_delta` | normal EDS - shuffled-keypoint EDS |
| `normal_vs_inverted_delta` | normal EDS - inverted-reward EDS |

Level-3 gate:

```text
RDT unguided on libero_object has nonzero SR or credible progress
+ normal EDS passes Level-0 and Level-1 gates
+ normal EDS SR is not worse than unguided by more than 10 percentage points
+ normal EDS beats zero/shuffled/inverted ablations on reward or progress
+ latency is reported and not pathological
```

If unguided RDT is still `0/10` on `libero_object`, checkpoint loading remains suspect and Level-3 success-rate judgment is blocked.

Qualitative evaluation is required because EDS can pass counter checks while still optimizing a visually wrong objective. These artifacts must be saved in reviewable files, not only shown in an interactive viewer.

Qualitative evaluation by level:

| Level | Required qualitative review | Saved output |
| --- | --- | --- |
| Level 0 | optional trace plots only if mock trajectories are available | `level_0_deployment_correctness.md` with route/counter screenshots or tables |
| Level 1 | required for every synthetic reward family and ablation | overlays, per-iteration population plots, and `level_1_mechanism_probe.md` |
| Level 2 | required for every smoke episode | videos, chunk overlays, and `level_2_online_smoke.md` |
| Level 3 | required for representative successes and failures on `libero_object` | videos, overlays, failure labels, and `level_3_libero_object_success.md` |
| Level 4 | required for at least one representative episode per LIBERO-PRO perturbation type | perturbation videos, overlays, failure labels, and `level_4_libero_pro_ood.md` |

For each representative `libero_object` and LIBERO-PRO perturbation run, save:

| Artifact | Purpose |
| --- | --- |
| `episode_video.mp4` | end-to-end behavior |
| `keypoints_projected.png` | inspect keypoint identity and indexing |
| `keypoints_selected_eef_overlay.mp4` | keypoints + selected EEF trajectory overlay in the policy/reward camera |
| `selected_trajectory_overlay.mp4` | selected EDS trajectory over the VLM camera |
| `best_trajectory_overlay_iter_<k>.png` | best trajectory overlay for every EDS `cem_iter` |
| `population_cloud_iter_<k>.png` | population trajectory cloud for every EDS `cem_iter` |
| `population_overlay_iter_000.png` | initial population spread |
| `population_overlay_iter_last.png` | final population convergence |
| `initial_best_vs_final_selected.mp4` | final selected action vs initial best action comparison |
| `normal_vs_zero_side_by_side.mp4` | verify steering effect visually |

| `normal_vs_inverted_side_by_side.mp4` | verify reward sign dependency |
| `eds_chunk_summary.csv` | quick per-chunk metrics table |
| `failure_review.md` | manual failure labels and notes |

Qualitative checklist:

1. Does the selected trajectory move toward the target keypoint or stage-specific direction?
2. Does the final selected trajectory differ from the initial best trajectory?
3. Does the population concentrate around higher-reward behavior over iterations?
4. Does zero reward remove apparent steering behavior?
5. Do shuffled keypoints degrade the selected trajectory?
6. Does inverted reward visibly move away from the desired target?
7. Are failures caused by base RDT action quality, wrong keypoints, reward mismatch, action-scale/sign mismatch, or environment/controller issues?

Qualitative gate:

```text
+ Under normal reward, the EDS selected trajectory should move toward the target keypoint
   or the stage-reward direction.
+ Across EDS cem_iters, the best trajectory and population cloud should show visible
   convergence toward the rewarded behavior.
+ The final selected action should differ from the initial best action in the intended
   reward-improving direction.
+ Zero-reward, shuffled-keypoint, and inverted-reward ablations should not show the
   same target-directed trend as normal reward.
```

If normal reward and zero/shuffled/inverted reward produce visually indistinguishable target-directed overlays, EDS deployment may still be correct, but algorithmic effectiveness is not established.

## 8. Ablation Matrix

| Ablation | What it tests | Expected result if EDS works |
| --- | --- | --- |
| Unguided RDT | base policy ability | baseline |
| EDS normal | target algorithm | improves reward/progress over unguided and ablations |
| EDS zero reward | whether EDS is only sampling | no systematic improvement; close to unguided/random |
| EDS random reward | robustness against meaningless score | worse than normal |
| EDS shuffled keypoints | keypoint dependency | worse than normal |
| EDS inverted reward | reward sign sanity | worse or opposite behavior |
| EDS no renoise | exploration dependency | weaker improvement |
| EDS no rollout after renoise | clean-action dependency | strongly worse; may select noisy artifacts |
| EDS p16 c10 | minimum viable config | fastest useful EDS |
| EDS p16 c20 | iteration sensitivity | better reward but slower |
| EDS p32 c10 | population sensitivity | better exploration but slower |
| EDS p32 c10 CEM | CEM vs probability resampling | either improved selection or premature collapse |
| action scale sweep | trajectory projection sensitivity | identifies scale mismatch in reward projection |
| coordinate sign sweep | action/frame sign sanity | normal sign should dominate |

The four required ablations are normal, zero reward, shuffled keypoints, and inverted reward. Without these, task success results are not attributable to EDS.

## 10. Failure Taxonomy

Each failed episode should be assigned one primary cause:

| Label | Definition |
| --- | --- |
| `ckpt_loading_error` | preflight indicates wrong RDT checkpoint or wrong weight variant |
| `base_policy_no_motion` | RDT produces weak or irrelevant actions even without guidance |
| `wrong_object` | keypoint/VLM guidance selected wrong object |
| `bad_keypoints` | detected keypoints are missing, on background, or poorly localized |
| `reward_misaligned` | reward improves while visible behavior worsens |
| `coordinate_mismatch` | trajectory moves in wrong axis/sign relative to keypoints |
| `action_scale_mismatch` | projected trajectory says progress, env action does not |
| `grasp_failure` | reaches object but cannot grasp |
| `transport_failure` | grasps but cannot move/place correctly |
| `libero_pro_setup_failure` | perturbation files, generated BDDL/init, or suite registration missing |
| `timeout` | partial behavior but no completion |
| `runtime_error` | exception, nonfinite value, API failure, asset failure |

This taxonomy is required because EDS can improve reward but still fail due to base RDT behavior, reward design, action projection mismatch, or LIBERO-PRO setup.

## 11. Statistical Reporting

For each method and suite:

1. Always report raw success count, denominator, and percent.
2. For runs with at least 10 episodes, report Wilson 95% confidence interval.
3. For small runs, do not over-interpret percentage gaps; compare raw counts.
4. Use paired seeds/task ids when comparing methods.
5. Report base `libero_object` and LIBERO-PRO `libero_object_*` perturbations separately.

Recommended summary table:

| Suite | Method | Episodes | Success | SR | Wilson 95% CI | Progress AUC | Mean final distance | Latency p50 | Wall-clock | Notes |
| --- | --- | ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: | --- |

## 12. Acceptance Gates

### Gate A: Deployment Correctness

Pass if all are true:

```text
EDS loop entered
+ score/resample/renoise/rollout counts match cem_iters
+ population scores finite
+ selected particle is actually best-cost particle
+ zero-reward ablation behaves like no-op / random selection
```

Expanded checks:

```text
+ population shape is `(population_size, 64, 128)`
+ `score_call_count = 1 + cem_iters`
+ `resample_count = renoise_count = rollout_count = cem_iters`
+ costs are finite and shape `(population_size,)`
+ final selected particle is `argmin(cost)`
+ action mask violations are near zero
+ no NaN/Inf in population, costs, probabilities, or decoded actions
```

### Gate B: Mechanism Validity

Pass if all are true:

```text
In >=70% guided chunks:
  final_best_reward > initial_best_reward
  OR target_distance_after < target_distance_before

+ normal reward outperforms zero reward
+ normal reward outperforms shuffled keypoints
+ normal reward outperforms inverted reward
+ selected particle reward is above final population mean in >=70% of chunks
```

### Gate C: `libero_object` Runtime Smoke

Pass if all are true:

```text
RDT checkpoint preflight passes
+ EDS completes real `libero_object` episodes without runtime errors
+ EDS reaches env.step() and writes videos/results
+ real keypoints and real guidance functions are used
+ normal EDS shows better reward/progress than zero-reward EDS
```

### Gate D: `libero_object` Success Evaluation

```text
RDT unguided on `libero_object` has nonzero SR or credible progress
+ normal EDS passes deployment and mechanism gates
+ normal EDS SR is not worse than unguided by more than 10 percentage points
+ normal EDS beats zero/shuffled/inverted ablations on reward or progress
```

### Gate E: LIBERO-PRO OOD Evaluation

```text
LIBERO-PRO preflight passes
+ EDS normal SR is nonzero on at least one `libero_object_*` perturbation
  OR EDS normal shows measurable progress improvement over unguided and ablations
```


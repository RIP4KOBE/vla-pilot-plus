## 工程问题与修复

### 可重复安装的仿真兼容性

干净环境首次 GPU 预检失败：Robosuite 原版要求 `MUJOCO_EGL_DEVICE_ID` 是 `CUDA_VISIBLE_DEVICES` 的成员，但本机 CUDA 与 EGL 枚举不同。该失败发生在仿真导入；同次 Codex 图像请求已经成功。

逐文件比较新装 wheel 与目前保留的旧在线环境，发现两份 Robosuite 文件存在兼容修改：设备编号校验、NumPy 2 分割图整数位宽、EGL 配置数组和上下文释放。此前安装文档未包含这些修改。

现在由 [兼容安装器](../../scripts/steering_dependency_compat.py) 和 [固定清单](../../scripts/dependency_patches/robosuite-1.4.0.json) 显式管理。它检查版本、全部输入和补丁哈希，验证全部输出后才替换包内文件；拒绝未知本地修改与当前 Python 环境以外的目标。预检与正式 launcher 检查安装结果，独立审计核对冻结补丁和依赖 receipt。首次补丁输出因混合换行格式未满足预期 SHA 而安全退出，未修改包；修正后输出与保留的旧环境逐字节一致。

两份旧文件的修改时间早于历史评测，但历史 receipt 没有记录其内部哈希。因此不能倒推此前每次运行的完整依赖字节身份。**新运行开始记录这些哈希。** 未修改模型、仿真参数、搜索、Stage/reward、提示词或判定阈值；这是将已有环境兼容行为纳入显式安装流程。

### GPU 与渲染设备验证

新增 [设备映射工具](../../scripts/list_steering_devices.py)，依据 UUID 和 EGL 扩展查找映射；GPU 预检进一步核对真实渲染 display。三张实际使用的 GPU 均已通过，避免“CUDA 张量成功但图像在另一张卡渲染”的安装误判。两个修复均属于安装、预检与审计；没有改变主线科学配置。修复后重新执行全套 CPU 回归和三组完整在线验收。

### 文档与下载路径

移除默认安装说明中已过时的 low 设置，补全三模式独立命令、依赖兼容步骤、显式软件源、浅子模块下载、LFS 等待和 LIBERO 校验复制路径。保留公开下载失败记录，不通过更换版本或关闭 TLS 校验绕过问题。研究文档改为方法、证据和开放问题的结构，历史身份集中到追溯索引。用于检查导入来源的辅助探针最初遗漏 launcher 的显式依赖路径，或未正确处理 namespace package，因而失败；修正探针后验证实际模块来源，未通过修改运行环境绕过检查。所有尝试保存在命令记录中。

## 与历史结果的可比性

与历史有效 ultra 对照相比，三种模式的十任务成败向量完全一致：VLS 成功 task 3，EDS 成功 task 3、8、9，EDS+QD 全部失败。历史 low 的 QD 为 1/10，属于另一协议，不与本轮拼接或混排。一次十任务的一致结果支持安装与运行链路恢复到可验收状态，不证明统计显著性或普遍泛化。

本轮保持任务、模型资产、RNG 恢复、动作执行、搜索、Stage/reward、提示词和在线协议。新 clone 与新环境运行的是明确受测提交；它相对起点只含兼容安装、设备预检、审计与相应测试修复。对历史有效 EDS receipt 的检查显示：15 个实际导入模块的版本与入口文件哈希均与新环境一致，Codex CLI 也一致。旧环境部分 distribution metadata 与真实导入版本不一致，不能仅凭 metadata 表判断实际运行版本不同。

限制是：旧 receipt 未记录全部依赖内部文件，在线服务也不可由客户端锁定其实现；GPU 分配和源码组织有所变化。本轮没有开展逐动作字节对齐或在线输出反事实实验，所以不能把成败一致写成完整轨迹相同，也不能声称恢复了一个月前的 Poe/Gemini 服务。它验证的是当前 Codex ultra 协议下的可重建环境与三模式链路。

当前可以从这套 main 开展算法开发，保留 EDS 作为对照。QD 的下一步应是失败轨迹归因、普通精英保留与 QD 的区分、描述符及父代消融；本轮没有开展这些算法实验。
